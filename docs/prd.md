# 如约 产品需求 v1.4

本文规定实验预览的产品范围与预期行为，不将规范本身视为验证结果。当前客户端为 `1.4.3` / `versionCode 12`；项目于 2026-09-30 暂停迭代，以半成品源码形式开放。运行方法见[开发指南](development.md)，验证入口与边界见[测试指南](testing.md)。

## 产品目标

让亲密关系双方把答应的事说清楚，并共同完成：建立关系 → 提出约定 → 对方接受 → 执行与提交 → 验收达成 → 奖励兑现。主状态链为待接受 → 待完成 → 待验收 → 待兑现 → 已兑现；任务达成和奖励兑现仍独立记录，兑现方标记已兑现后结束。

## 首版范围

- 安卓优先；两名真实账号可以分别使用设备，服务端保存共享状态。支持亲子、情侣、自定义两人关系，一人可以有多个隔离关系。
- 无独立设备的孩子由家长建立档案并代记，所有相关动作和结案显示代记来源，不冒充孩子独立确认。
- 一次性任务与累计目标共用约定对象。累计目标记录进度，达到目标后统一提交验收。每条约定一名执行者、一名验收及奖励给予者、一份整体兑现的奖励。
- 约定含标题、验收条件、完成截止（可不限期）、目标次数、奖励描述、达成后的兑现天数。默认 1 次、7 天兑现，用户可修改。
- 草稿、发布、接受/拒绝、记录进度、文字/图片提交、退回补充、验收、奖励兑现、协商修改、取消、关系解除和完整历史。
- 四个入口：首页待办、约定、奖励、关系。支持关系/状态筛选；奖励筛选为全部、待兑现、已兑现，行内区分本人和对方的兑现/获得角色。
- 首版提醒为应用内待办与逾期提示，打开或刷新时同步。后台系统推送是后续能力，不将应用内提醒描述成推送。

## 硬规则

1. 发布不等于生效，对方接受后开始；角色按约定确定，不固定关系中的上下级。
2. 生效后的条件、期限、奖励不得单方改写。变更提案经另一方确认才生效，旧内容和操作人可追溯。
3. 及时提交后等待验收，不因审核延迟变成失败。超期未提交标记到期，延期经双方确认后才能继续。
4. 验收通过产生奖励待兑现；只有兑现方可标记已兑现，成功后结束，不再提供接收方收讫或未收到反馈动作。此规则自 1.4.0 起替代此前双重确认要求。旧 `offered` 奖励读取为已兑现，保留原给出及其他历史，不补造接收方确认。
5. 到期、归档、关系解除均不抹除已产生的奖励。达成后的普通取消被拒绝；奖励替换须接受者同意。
6. 家长代记关系可以由家长完成流程；关系、操作与结案继续显示代记来源，不能把家长操作呈现为孩子独立确认。
7. 关系解除停止新增约定与普通互动；双方可以查看已有共同记录并处理既有奖励结算。新关系不会获得旧关系权限。
8. 奖励在应用外给付；首版不接入支付、积分商城、陌生人任务市场、自动惩罚、公开排行或 AI 裁决。

## 体验与信息结构

日常页按关系分组展示待跟进约定，行内明确待我处理还是等待对方；待兑现奖励继续保留跟进入口，已兑现退出待办。约定与奖励页按关系 ID 分组，显示关系名称、成员、记录数量；每条记录用紧凑整行入口呈现标题、状态、角色与进度/期限，完整条件和奖励在详情中查看。详情以当前动作、单一“进度记录”、条款与奖励组织；进度记录合并创建、接受、进度次数、说明、照片、提交、验收、兑现及后续变更历史，按时间和事件身份清楚关联，不把同一次进度重复展示为两条记录。原有独立进度块、事件块和“留下说明”入口不再并列出现；记录进度与提交时仍可填写说明、附照片。只有有权执行的关键动作使用强调按钮。创建使用小型按钮，查看使用整行入口，修改/返回等次操作使用文字按钮。业务界面避免大块情绪文案；日常与奖励各保留一句点缀，插画不挤占实际操作。

主状态链是对任务与奖励字段的组合展示，不删除任务达成事实。草稿、拒绝、取消、到期和补充重提仍保留原分支；提交验收前不能仅凭次数达标显示已达成，验收后仍须等待兑现方标记才显示已兑现。历史说明、旧收讫及分歧事件继续可读，其内容不能被改写成新规则下发生的操作。

四页默认查看全部关系，顶部不常驻关系筛选栏。关系数量大于 1 或已有关系筛选时，在“我们”页操作区显示轻文字入口“查看范围”；点击后在弹窗中选择关系并点击“应用范围”，返回取消不改变选择。查看范围仍由四页共享，选中的关系在操作区下方说明；恢复全部也通过该入口。同步信息只在同步中或有反馈时显示，无消息时不占位。

排版使用统一的 24dp 页面边距与 16dp 卡片内边距；文本自身不暗加上下留白，层级间距显式使用 4、8、12、16、24dp。四页只保留一个页标题，列表标题、状态和归属分行，长标题不与状态标签争抢宽度。同关系条目使用一张列表底板与细分隔，关系头与条目保持清楚边界。按钮视觉尺寸与触控区域分开处理，短操作仍保留至少 48dp 触控高度。验收必须查看多关系、长文本、窄屏和大字的真实原生截图。

顶部不得恢复常驻“全部关系”栏，范围筛选保留在“我们”页；此规则只适用于本 APP 的公共顶部关系栏，仍须通过设备与视觉验证。

品牌为“如约”，视觉使用珍珠暖白、玫瑰珊瑚、淡紫灰与交叠环线，日常和奖励各用一组扁平插画作克制点缀。列表与表单保持清楚的关系边界、排版和操作层级；窄屏、大字体、状态可辨认与单手操作仍需检验。素材来源见[插画说明](design/ruyue-illustrations.md)。

创建使用全屏三步：选择关系并填写目标与截止 → 约定奖励及兑现时间 → 核对完整条款与双方角色。前两步只编辑本地表单，返回上一步保留输入；最后才发出约定或存为草稿。失败保留表单，同一内容重试沿用幂等身份。发出后必须等待对方接受，达到累计次数后仍需提交与验收。

示例均为合成数据：数学达到约定成绩后获得一次科技馆活动；本月共同运动八次后由对方安排一次晚餐。示例不自动写入用户账号。

## 验证与边界

验收见 [首版验收](acceptance.md)，状态与接口见 [共享契约](api.md)，技术与数据见 [架构](architecture.md)。真实用户试用、留存和付费证据尚未获得。重点观察首次双人闭环、奖励等待时间及再次创建约定，不能只统计任务完成数。

本地服务和调试 APK 用于开发验收；公网 HTTPS 服务、生产签名、账号找回、运维与商店发布需要单独落实，不能把本机双设备验证描述成已上线。
